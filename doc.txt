28. Final Product Rules
1. Product Definition
Product name: Dayflow
Category: Human Resource Management System (HRMS)
Primary users: Admin/HR Officer and Employee
Core promise: Every workday, perfectly aligned.
Dayflow centralizes employee information, attendance, leave, approvals and payroll visibility in one structured application.
Product direction
Dayflow should look and behave like a real business application, not a college prototype. Every visible metric should come from real application data once backend integration is complete.
2. Problem Statement
HR operations are often spread across separate processes for employee records, attendance, leave requests, approvals and salary information. This creates duplicated work, poor visibility and disconnected employee/HR workflows.
Dayflow solves this by creating a centralized HR workspace with role-specific access and connected workflows.
2.1 Core problem to demonstrate
Employee → works → attendance is recorded
Employee → needs time off → submits leave
HR/Admin → reviews → approves/rejects
Employee → views → updated status
HR/Admin → manages → employee and payroll information
3. Product Goals
Digitize core HR operations.
Provide secure role-based access.
Give employees a simple self-service HR experience.
Give HR/Admin users centralized management and approval tools.
Maintain real relational data with clear relationships.
Provide reliable CRUD workflows.
Prevent unauthorized access to employee and payroll information.
Provide a polished responsive interface.
Make the architecture simple enough for every team member to explain.
Meet the Odoo virtual-round engineering priorities before adding optional features.

8. UX/UI Design System
The final UI should follow a modern professional HR SaaS/dashboard visual language. The supplied Excalidraw design should be treated as the visual reference for the intended information layout; the implementation must preserve its core screen hierarchy while making the final UI polished and usable.
8.1 Design principles
Simple + polished is better than overloaded.
Clear visual hierarchy.
Consistent spacing and typography.
Primary actions must be obvious.
Tables must be readable.
Forms must provide immediate validation.
Every async operation needs loading/success/error feedback.
Responsive layout.
Do not use decorative animation when it does not improve usability.

14.2 Data rules
Unique email and employee code.
Foreign keys prevent orphan records.
One logical attendance record per employee/work date.
Leave end date cannot precede start date.
Employees cannot approve their own leave.
Payroll access is role-protected.
Use transactions for multi-step state changes.

16. Authentication & Security
Hash passwords; never store plaintext.
Use JWT for authenticated API access.
Enforce authorization at backend endpoints.
Validate all request bodies.
Do not expose sensitive fields in DTOs.
Protect payroll and employee data.
Use environment variables for secrets.
Use HTTPS in deployment.
Log important admin/security events.
Never return stack traces to users.

22. Antigravity Build Instructions
This section is the direct execution contract for Antigravity.
22.1 Build rules
Read this document before creating code.
Do not replace PostgreSQL with static JSON.
Do not replace the backend with frontend-only logic.
Do not add unnecessary third-party APIs.
Do not add AI unless a specific approved HR use case is defined.
Do not create fake dashboard metrics once APIs exist.
Implement modules incrementally and keep the application runnable after each phase.
Use reusable components rather than duplicated UI.
Keep business rules in services, not controllers.
Use DTOs and validation.
Protect all sensitive endpoints.
After each phase, test the feature before starting the next phase.

Finish core workflows before optional features.

FINAL TECHNOLOGY DECISION
Frontend: React + TypeScript + Vite + Tailwind CSS + shadcn/ui
Backend: Python 3.12+ + FastAPI + SQLAlchemy 2.x + Alembic + Pydantic
Database: PostgreSQL
Authentication: JWT + secure password hashing
Development: Antigravity + Git/GitHub + Docker + Postman + pgAdmin
Java and Spring Boot are NOT part of the final Dayflow implementation stack.
This is an implementation choice. The Odoo Hackathon evaluation guide emphasizes real database design, working backend APIs, CRUD, validation, UI/UX, security, testing, team collaboration and explainable architecture; it does not mandate Java or Spring Boot.
